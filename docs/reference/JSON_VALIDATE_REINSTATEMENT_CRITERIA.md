# JSON バリデーション再導入基準

## 概要

このドキュメントは、StreamConverter における JSON スキーマバリデーション機能の再導入に関する要件定義と判断基準を記録します。

## 背景

JSON バリデーション機能（`JsonValidateCommand` など）はかつて実装されていたが、以下の理由により一時的に縮小・保留状態となっています：

- スキーマ検証ライブラリのバージョン互換性問題
- ストリーミング処理との整合性確保の複雑さ
- メモリ効率への影響懸念

本 issue (#456) では、**再導入時に満たすべき要件** を明文化し、将来の実装判断の基準とします。

## 再導入の必要条件

### 機能要件

1. **スキーマ検証の正確性**
   - JSON Schema Draft 2020-12 に準拠すること
   - `required`, `type`, `format`, `enum`, `pattern` などの主要キーワードをサポートすること

2. **ストリーミング互換性**
   - `IStreamCommand.execute(InputStream, OutputStream)` の契約を遵守すること
   - JSON Schema は全体構造を要求するため真のストリーミング検証が困難であることを踏まえ、以下のいずれかのアプローチを採用すること：
     - (a) **構文検証のみ**: 入力全体をメモリにロードせず、トークン単位の検証に限定する
     - (b) **制約限定スキーマ検証**: `required`/`type` など構造を要求しないキーワードのみを対象とし、要素単位で検証する
     - (c) **サイズ上限付き非ストリーミング検証**: 入力サイズ上限（例: 10MB）を明示し、上限内は全体ロードを許容する
   - バリデーション失敗時は `StreamProcessingException` でラップして伝搬すること

3. **エラーレポート**
   - バリデーション失敗時に、失敗したフィールドパスとルールを含むメッセージを提供すること
   - `ValidationResult` クラスを活用してエラー情報を格納すること

### 非機能要件

4. **メモリ効率**
   - 100MB 以上の JSON ファイルに対して定常メモリ使用量が入力サイズの 10% 以下であること
   - `MemoryEfficiencyTest` の既存テストケースに合格すること

5. **パフォーマンス**
   - バリデーションのオーバーヘッドが処理時間の 20% 以下であること

6. **テストカバレッジ**
   - ラインカバレッジ 90% 以上
   - 正常系・異常系・境界値のテストケースを網羅すること

### 依存関係要件

7. **ライブラリ選定**
   - 採用するバリデーションライブラリは以下を満たすこと：
     - Java 21 互換
     - ストリーミング API をサポートするか、パーシングと分離可能な設計であること
     - セキュリティ上の既知脆弱性がないこと（CodeQL チェック通過）
   - 候補: `com.networknt:json-schema-validator` (現行依存)、`dev.harrel:json-schema`

## 再導入を保留する理由（現状）

以下の条件が解消されるまで実装を凍結します：

| 条件 | 状態 | 解消見込み |
|------|------|----------|
| ストリーミング JSON バリデーションの設計パターン確立 | 未完了 | PR-E (実行戦略) 完了後 |
| `ExecutionStrategy` / `ErrorPolicy` 基盤の整備 | 未完了 | PR-E (#503-#505) |
| `Source` / `Sink` 統一 API の整備 | 未完了 | PR-G (#507) |
